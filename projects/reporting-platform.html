Case study · Data engineering

Unified Reporting Platform

Firm data lived in several systems that didn't talk to each other, and every question about it became an engineering request. I built the pipelines to bring those systems into one reporting layer — then made that layer self-serve.

Context
Reese Law Group
Role
Pipeline design, DBA, reporting
Stack
Python · SQL · Airflow · Snowflake · Power BI
Outcome
Self-serve reporting, no engineer in the loop

The problem

Ask a simple operational question — how many matters are at a given stage, how a department's volume is trending — and answering it meant opening three systems, exporting from each, and reconciling them in Excel. Every answer was a one-off. Two people asking the same question a week apart could get two different numbers.

The bottleneck wasn't the reporting. It was that every report started from scratch.

The approach

1. Land the data once, centrally

Scheduled pipelines extract from each internal source on a fixed cadence and land it in a central warehouse. From that point on, every report reads from one place. The arguing-about-whose-export-is-right problem disappears when there's only one export.

2. Model it for the questions people actually ask

Raw operational schemas are shaped for transactions, not analysis. A modelling layer sits on top: cleaned, conformed tables with the business definitions baked in, so "open matter" means the same thing in every report that uses it.

3. Schedule and monitor, don't babysit

Orchestration handles dependencies and retries, and a failed load announces itself rather than quietly serving yesterday's numbers. A stale dashboard nobody knows is stale is worse than no dashboard.

4. Hand over the keys

The last step is the one that actually removed the bottleneck: no-code reporting applications on top of the modelled layer, so admin and compliance staff could filter, slice, and pull what they needed without an engineering ticket.

Engineering decisions worth calling out

  • Raw layer stays immutable. Land it as it arrived, transform downstream. When a definition changes you rebuild from raw instead of re-extracting from production systems.
  • Definitions live in the model, not in each report. Otherwise every dashboard slowly grows its own private version of the truth.
  • Self-serve beats more dashboards. Building the twentieth dashboard is a treadmill; giving people a safe way to answer their own questions gets you off it.
  • Query optimisation as a habit. Reports people wait on are reports people stop using. Indexing and query shape got attention early, not after complaints.

Data governance

Later, at Frantz Law Group, the same instinct showed up as explicit governance work: documenting definitions, tightening quality checks at ingestion, and making data discoverable firm-wide. Consistency is a feature — it's what lets someone trust a number they didn't produce themselves.

The measure of success here isn't dashboard count. It's how many questions get answered without anyone asking an engineer.

Results

  • ▸Siloed internal systems consolidated into one reporting layer used across the firm.
  • ▸Admin and compliance staff got direct, self-serve access to firm data with no engineering support.
  • ▸Recurring ad-hoc requests were converted into scheduled, repeatable outputs.
  • ▸Governance processes improved data quality, consistency, and accessibility firm-wide.

What I'd do differently

I'd write the data contract with each source system earlier. Most pipeline breakages weren't logic bugs — they were an upstream column quietly changing type or meaning. Explicit expectations at the boundary, checked on every load, would have turned those from mysteries into alerts.
